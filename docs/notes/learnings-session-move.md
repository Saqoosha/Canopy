# Session move

Moving a live session to another folder: the `move-session` skill, `canopyctl move`, `move_session`, `ShimProcess.requestMove`, `SessionMove`, `SessionStore.noteMove` and `restartAfterMove`. Why it exists and what was measured: `docs/superpowers/specs/2026-11-06-no-folder-session-design.md`.

- **`set_cwd` is a stream-json control request, and the shim writes it.** The extension has `Query.setCwd` and never calls it. The wire and the answers are in `Resources/vscode-shim/cli-control.js` and `SessionMove.parseReply`. The key is `path`, not `cwd`. The CLI moves the transcript itself.
- **`/cd` does not help.** It is TUI-only: stream-json answers `/cd isn't available in this environment.`
- **The restart is required.** After `set_cwd` alone the next turn worked, but a webview reload hung on `Loading...`. A restart in the new folder fixed it, so `restartAfterMove` does what `moveToCheckout` does.
- **Two steps.** On the CLI's `ok`, `noteMove` records the new folder on the session at once, so a restart for any other reason also starts there. The restart itself waits.
- **Nothing moves while work runs.** The skill asks from inside a turn, so `SessionMove.Latch` waits on `restartLosesWork`, for `set_cwd` and again for the restart. A `result`, or a background task clearing, tries again. The CLI still answers `busy` right after a turn, which is what `busyRetryLimit` covers.
- **`needs_trust` is the normal path on a first move**, because Canopy's launch path shows no trust dialog. The CLI records an accepted answer for the whole repository, worktrees included. Cancel sends nothing, so the next move there asks again.
- **The alert shows only when config could have come from outside** (`SessionMove.scanTrust`). Config means a `.claude` folder (agents and skills can declare MCP servers and allowed tools, not just settings) or a `.mcp.json`. It asks when one sits in a folder above (the CLI loads ancestor `.mcp.json`), when git tracks one in any checkout of the repository, or, outside a repository, when one exists anywhere below. A walk that cannot finish, or stops at `scopeEntryLimit`, asks too. Untracked config counts as made on this Mac. A tarball unpacked into a repository is the gap that leaves. A checkout is skipped when its origin owner is in the `canopy.trustedRemoteOwners` default (empty unless set) and its HEAD is on an origin branch, so a fork's PR checked out locally is still scanned. Names match case-insensitively, as the default volume does. Measured on 2026-11-11 without owners: 13 of 97 untrusted repositories here and 16 of 149 on studio would ask.
- **Contents never decide.** Foundation's `JSONSerialization` keeps the first duplicate key, and the CLI keeps the last (measured), so a JSON scan cannot vouch for what the CLI runs. `configSummary` only fills the alert.
- **Trust outlives the check.** It is keyed by path, so a later pull that adds hooks runs them unasked. A trust the user accepted behaves the same way.
- **The trust answer stays off the local socket.** Any process of this user can open it, so a frame to the GUI and an answer back would let a session approve a folder through Canopy. The daemon raises a `CFUserNotification` itself (`SessionMove.HostTrustAlert`). Keep it that way: no trust argument on `move_session`. This does not guard the CLI's own trust file, which a session with Bash can edit.
- **A Mac viewing the session over TCP is asked too.** Otherwise a move asked for from a mirror pane waits on a screen nobody is at (studio) and times out. The question goes out as a `MirrorUIFrame.alert` (Cancel, Move), so a Mac on an older build answers it as well, and only to clients with `acceptsUI` that are not on the local socket (`ShimProcess.trustViewers`). Those passed the mirror password, which lives in the Keychain; a session's Bash reading it raises a Keychain prompt. The first yes or no settles it (`SessionMove.TrustRace`), cancels the host alert and sends the viewers `dismissAlert`, which a Mac on an older build drops, so its alert stays and its answer is ignored. A Mac that attaches after the question went out is not asked. A failed move also shows an error banner in those panes.
- **The GUI follows a rise in `moveCount`.** `followsCheckoutMove` stays as it is, because one path spelled two ways must not restart a pane. A new daemon counts from 0 again.
- **Typed text in the composer:** the restart rebuilds the webview, so text typed between the end of the turn and the move is lost. Read from the code, not measured.
- **Known gaps:** a `set_cwd` the CLI never answers keeps the move waiting, with no timeout, because a late answer after one would leave the CLI moved and Canopy not. `transcript_relocated: false` is not handled.
- **The resume writes a filler line.** `set_cwd` writes a meta user record, and the resume answers it with a `<synthetic>` `No response requested.` The CLI never streams it (CLI 2.1.319, measured), so only a replay would show it, and `strippingNoResponseFillers` drops it there.
