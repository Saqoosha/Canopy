# ペイン並べ替え設計

サイドバーの open 行をドラッグして、マルチペインの左右位置を入れ替えられるようにする。

## 原則

サイドバーの open ブロックは、ペイン列の地図として読める。ペイン付き行を上から読むと、ペインの左から右。

その対応を保つために動かすものは、**片方だけ**と決める。

- ドラッグしたとき → 動くのは**ペイン**。ユーザーが行を掴んだのだから、行はユーザーが置いた場所に留まる
- ペイン割り当てが変わったとき → 動くのは**行**。ユーザーがそのペインを選んで中身を入れたのだから、ペインは動かさない

逆にすると必ず裏切る。ドラッグで行を動かせばユーザーの手の下から行が逃げるし、クリックでペインを並べ直せば、いま中身を入れたペインが別の位置へ飛ぶ。

**純粋な選択では何も動かない。** 既にペインにあるセッションを選び直しても `openInFocusedPane` は focus するだけで、行にもペインにも触れない。

### 当初の設計とその破棄

最初はズレを許容する設計にした（ドラッグのときだけペインが動き、それ以外の経路ではサイドバー順とペイン順が食い違ってよい）。実機で破綻した。真ん中のペインにフォーカスしたままペインなしのセッションをクリックすると、その行はサイドバーの一番上にあるのに中身は真ん中のペインに出る。背景色でズレは見えるが、読めることと納得できることは別だった。

ズレを許容した理由は「行が勝手に動くのを避ける」ことだった。それは**ランク一致時の no-op**（「変更点 3」参照）で解ける。行が動くのは対応が実際に壊れているときだけになる。

ただし「新規セッションでは絶対に動かない」ではない。`openNew` の既定は `target: .focused` なので、既存のペインに開く経路（Cmd+O、ランチャーの Start、閉じた行の素クリック）では、フォーカス中のペインが最も右の session ペインでなければ新しい行もそのペインの順位まで動く。それは仕様どおりの動作。

## 変更点

3 箇所。ほかに UI として、サイドバーの行順に 0.2s のアニメーションを付け、ペイン所属のハイライトを角丸チップ化した（`listRowBackground` はインセットを食うので、ホバー塗りと同じインラインの `.background` に移した）。

### 1. open 行の Cmd+click は「その行に専用ペインを」

`openInNewPane` はペインを append したあと `syncPaneOrderToRows()` を呼ぶ。**新しいペインは、その行がいる位置へ落ちる。** 一番上の行を Cmd+click すれば左端。行は 1 行も動かない。

これが原則の「狙ったものが残る」に対応する。Cmd+click が指しているのは**行**（「この行に専用ペインを」）なので、行が主でペインが動く。素クリックが指しているのはフォーカス中の**ペイン**なので、ペインが主で行が動く。

右端に append しっぱなしにすると、行がどこにいようとペインが右端に出る。それが「サイドバーが勝手に並べ替わって見える」の正体だった。

`bouncePane(forSessionId:)` はこの分岐からしか呼ばれていないため、デッドコードとして削除する。

### 2. ドラッグでペインを追従させる（`syncPaneOrderToRows`）

`SessionStore.moveOpenSessions` の末尾で `syncPaneOrderToRows()` を呼び、session ペインを行の順に並べ直す。

```text
openSessions:  A  B  C  D          panes: [A][B][C]
C を B の上へドラッグ
openSessions:  A  C  B  D    →     panes: [A][C][B]
```

アルゴリズム。**session ペインを、その行の `openSessions` 内の位置で並べるだけ。**

これが成立するのは変更点 3（ペイン割り当て時に行が動く）とセットだから。ドラッグ以外に両者をズラす経路が存在しないので、「溜まったズレが並べ替えで吹き飛ぶ」という懸念そのものが消える。

**当初は「ドラッグされたペインだけを動かす」targeted 版で実装し、レビュー（PR #126）で 3 つの順序バグを出した** — 複数行ドラッグ、フィルタで隠れたペインを跨ぐドラッグ、それにペインなし行が混ざった場合。全部が index 計算の誤りで、ソートはその計算をしないので該当ケースを持たない。**ズレが発生しうると再証明できない限り、targeted 版に戻さないこと。**

補足規則。

- launcher ペインはサイドバー行を持たないのでスロット位置に留まり、session ペインがその周りで並べ替わる
- フィルタで隠れた行の特別扱いは要らない。`reorderPreservingHidden` が隠れた行をマスター位置に留めるので、`openSessions` の順をそのまま読めば織り込み済みになる
- ペイン同士の相対順が変わらないドラッグ（ペインなし行のドラッグ、ペインなし行を跨いだだけのドラッグ）は結果が同じ並びになり、何も起きない
- `focusedPaneIndex` は移動後の同じ `PaneSlot.id` を指し直す。位置ではなく**スロットの同一性**に追従するので、フォーカス中が launcher ペインでも壊れない

### 3. ペイン割り当てで行を追従させる（`moveRowFollowingPaneAssignment`）

`openInFocusedPane` の中身差し替え分岐と `openInNewPane` から呼ぶ。そのセッションの行を、ペインの順位に対応する位置へ移す。ペインは動かさない。

**ランクが既に一致していれば何もしない。** これは最適化ではなく、静けさの担保。`openInNewPane` 経由（行の append とペインの append が同時に起きる）では常に一致するので一度も動かない。逆に `openNew(target: .focused)` で既存のペインへ開く場合は動く — 上の「当初の設計とその破棄」に書いたとおり、それは仕様。

着地点は「その順位の直前のペイン行の隣」。「次に来るペイン行の直前」でも順位は満たせるが、間にあるペインなし行の向こう側まで飛ぶぶん移動量が大きい。

`syncPaneOrderToRows` と違ってフィルタを見ない。編集対象はマスターの `openSessions` 順で、それはフィルタを外したときに正しくあるべき順だから。

## 幅とアイデンティティの扱い

移動単位は `PaneSlot` 全体。`content` だけを入れ替えてスロット位置を固定する案は採らない。理由が 2 つある。

幅がセッションに追従する。`preferredWidth` が一緒に動くのでペインの合計幅が変わらず、ウィンドウのリサイズが起きない。各 WKWebView は幅が変化しないまま x 座標だけ移動するため再レイアウトが走らず、チャットのスクロール位置がずれない。

SwiftUI の identity が保たれる。`Detail.swift:113` で `SessionContainer` は `.id(session.id)` を持つ。`PaneSlot` ごと動かせば `ForEach(id: \.element.id)` から見て要素の移動になり、部分木はそのまま運ばれる。逆にスロット位置を固定して `content` だけ交換すると、そのスロットの `.id(session.id)` が別の値に変わり `SessionContainer` が破棄・再構築される。`OpenSession.webView` のキャッシュがあるため致命傷にはならないが、避けられる churn を自分から呼び込むことになる。

`normalizePaneWeightsToVisualWidths()` は呼ばない。この操作は `preferredWidth` を絶対 pt として解釈せず、要素を入れ替えるだけだからである。`schedulePaneResize()` も呼ばない。合計幅が不変でウィンドウを変える理由がない。

## 変更しない点

- バッジも、open ブロックの段分けも入れない
- `closePane` / `removePanesForClosedSession`: 要素の削除は相対順を壊さない
- `cycleFocusedPaneSession` / Cmd+Ctrl+1..9: 実装は不変。ただし `openInFocusedPane` を通るので、変更点 3 の結果として行は動くようになった
- 閉じたセッション行の Cmd+click（新しいセッションを新ペインで開く）と New Session ボタンの Cmd+click（launcher を新ペインで開く）は現状維持。前者は行が末尾に append されるので、ペインも末尾のまま動かない

## テスト

`_SidebarLogicProbe` に追加する。プローブは既に `SessionStore` を直接組み立てて `openInNewPane` などを叩いているので、同じ形で書ける。

- 隣接する 2 ペインの入れ替えで `panes` の順が入れ替わる
- 入れ替え後、各 `preferredWidth` が対応するセッションに付いて動いている
- 並べ替え前後で `panes.count` と `preferredWidth` の総和が不変
- ペインなしの open 行を挟んだドラッグがペイン順を変えない
- ペインを持たない行のドラッグがペインを一切変えない
- launcher ペインが index に留まり、その両側の session ペインだけが並べ替わる
- `focusedPaneIndex` が移動後も同じセッションを指す
- 複数行ドラッグ（下方向・上方向の両方）でペイン順が行の最終順と一致する
- ペイン付き行とペインなし行を混ぜてドラッグしてもペイン順が行順と一致する
- open 行の Cmd+click で新しいペインがその行の位置に生え、行は動かない（一番上の行なら左端）

フィルタ絡みは 2 件テストする。隠れたペインを跨ぐドラッグと、そこにペインなし行が混ざる場合（targeted 版が壊れたのはこの 2 つ目）。あわせて、プローブが読む `visibleRows` は開発者の保存済みフィルタに影響されるので、ブロック先頭で永続値を中立化し末尾で戻す — さもないと CI では通ってローカルだけ落ちる。

`ci.yml` の `EXPECTED_ASSERTIONS` を、追加後の実測値まで引き上げる。

## リスクと確認事項

`ForEach` の要素移動が SwiftUI 上で本当に移動として扱われ、再マウントにならないことは実機で確認するまで断定しない。上の identity 分析は再マウントが起きない根拠だが、macOS 26 の SwiftUI はマルチペイン周りで既に一度裏切っている（`WeightedPaneLayout` の学びを参照）。実装後、2 ペインを入れ替えてチャットのスクロール位置が保たれることを目視で確認する。

`rowClickBinding` は open 行のクリックを `List` の selection setter で受けている（tap gesture を足すと `.onMove` が死ぬため）。macOS は selection を mouse-down で書くので、**ペインを持たない open 行を掴んだ瞬間**に `openInFocusedPane` が走り、その行が動く。ドラッグ後に `syncPaneOrderToRows` が走るので最終状態は整合するが、`.onMove` の offset が影響を受けるのか見た目が跳ねるだけなのかは静的には判定できない。

ここは直していない。修正にはドラッグ中フラグが要り、キャンセルされたドラッグでフラグが下りなかったとき（Mission Control / Spotlight / Cmd+Tab — `DragCursorLock` で既に踏んで FB13559963 として記録済み）、行追従がセッション中ずっと黙って死ぬ。より静かなバグとの交換になる。
