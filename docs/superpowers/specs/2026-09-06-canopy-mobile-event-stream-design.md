# Canopy Mobile — セッションイベントのストリーミング設計

**目的**：iPhone で、セッションで「いま何が起きているか」を会話として読めるようにする。今日届くのは完了時と許可要求時の push だけで、その間の数十分は何も見えない。

**日付**：2026-09-06
**関連 spec**：`2026-09-03-canopy-mobile-design.md`（roster と通知の土台）、`2026-09-04-canopy-mobile-history-design.md`（通知履歴）

---

## 決まっていること

3 つの選択が設計を固定している。どれも実装の都合ではなく、使う側の判断として選ばれた。

**解像度は「完成した発言」**。トークン単位の `content_block_delta` は転送しない。文が出来上がってから 1 通として届く。

**ツールは名前＋一行要約まで**。引数も結果も relay を通さない。「黙っていない、何かやっている」が分かればいい。

**遡れるのは直近だけ**。全 transcript のバックフィルはしない。

## 非目標

トークン単位のストリーミング。ツールの引数と結果。全履歴のバックフィル。イベント列から返信する経路（返信は既存の `/reply` のまま）。シムが生きていないセッション。

---

## アーキテクチャ

```
ShimProcess（io_message を見る）
  └─ SessionEvent を作る ──→ RosterPublisher の既存 WebSocket
                                    │  {type:"event", …}
                                    ▼
                              MachineDO（relay）
                                ├─ seq を採番して SQLite に追記
                                ├─ セッションごとに直近 N 件へトリム
                                └─ watcher へ即 fan-out
                                    │
                                    ▼
                              iPhone（前面のときだけ）
                                ├─ SessionEventStore に積む
                                └─ SessionConversationView が描画
```

**新しい配管はない**。publisher ソケット・watcher ソケット・DO はすべて既存で、`/publish` と `/watch` の経路もそのまま。増えるのは publisher が送るメッセージの種類が 1 つと、DO が保存するテーブルが 1 つ。

### バッファを DO 側に置く理由

Mac 側にバッファを置いて購読時に再生する案も検討し、却下した。DO 側に置くと「誰も見ていない時間」にも保存コストがかかるが、**Mac が落ちた直後でも直近が読める**。この一点を取る判断。

代償として、**publisher ソケットが切れている間に生まれたイベントは失われる**。Mac 側にもバッファを置けば埋まるが、それは保険の二重掛けであり、DO 側に置いた意味を消す。欠点として受け入れる。

### 前面限定であること

WebSocket はアプリが前面にある間しか生きない。iOS はバックグラウンドでソケットを切る。**このライブ表示は前面限定の機能**であり、バックグラウンドの通知経路は今まで通り APNs のまま。両者は置き換え関係ではない。

## イベントの種類

4 種のみ。

| 種類 | 中身 | 出所 |
|---|---|---|
| `assistant` | 完成したテキスト 1 通 | `assistant` フレームのテキストブロック |
| `user` | ユーザーの発言 | `user` フレーム — **tool_result を含むものは除外** |
| `tool` | ツール名＋一行要約 | `tool_use` ブロック |
| `turnStart` / `turnEnd` | turn の境界 | `system/init` と `result` |

**`user` フレームの大半は tool_result である**。除外を落とすと会話がツール結果で埋まる。ここが実装で最も壊れやすい判定で、probe で固定する。

### 一行要約に入れるもの

一行要約は relay を通るので、**何を入れるかはツールごとに列挙して決める**。列挙にないツールは名前だけになる。既定が「名前だけ」であることが要で、新しいツールが増えたときに黙って中身が漏れ出さない。

| ツール | 要約 | 例 |
|---|---|---|
| `Bash` | コマンドの 1 行目、80 文字で切る | `Bash: npm test` |
| `Read` / `Edit` / `Write` | パスの**ファイル名のみ**（ディレクトリは落とす） | `Edit: SessionStore.swift` |
| `Glob` / `Grep` | パターン、80 文字で切る | `Grep: sendPush` |
| `Task` / `Agent` | `description` | `Task: review the diff` |
| 上記以外 | 名前だけ | `WebFetch` |

**ディレクトリを落とすのは意図的**である。ファイル名は「何を触っているか」を伝えるが、絶対パスはマシンの構造そのものを外に出す。差分・ファイル内容・ツールの実行結果はどのツールでも送らない。

---

## seq と eventId — 役割が違う 2 つの識別子

**`seq`**：DO が振る単調増加の連番。順序と再開に使う。電話は最後に見た seq を覚え、再接続時に `seq > n` を要求する。採番の単位は DO 全体であって、セッションごとではない（理由は「DO のスキーマ」節）。

**`eventId`**：Canopy がイベント生成時に振る id。**経路をまたいだ同一性**に使う。`completed` push にも同じ id を載せるので、電話は同じ id の通知アイテムを二重に描画しない。

**1 つで兼ねられない**。seq は DO が振るので、Canopy が push を出す時点では知り得ない。逆に eventId だけでは「n より後を全部」を安く問い合わせられない。

---

## DO のスキーマ

DO は SQLite バックエンド（`wrangler.toml` の `new_sqlite_classes`）で、既に `ctx.storage.sql` のテーブルを 1 つ持っている。イベントは 2 つ目のテーブルとして素直に載る。

```sql
CREATE TABLE IF NOT EXISTS event (
  seq        INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id TEXT NOT NULL,
  event_id   TEXT NOT NULL,
  kind       TEXT NOT NULL,
  text       TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS event_by_session ON event (session_id, seq);
```

`seq` は DO 全体で単調増加させ、セッションごとの連番にはしない。電話が 1 本のソケットで全セッションのイベントを受けるので、**再開の問い合わせも 1 本で済む**ほうが素直だからである。セッションごとの順序は `session_id, seq` の索引が与える。

### 上限と追い出し

| 対象 | 上限 | 根拠 |
|---|---|---|
| 1 セッションのイベント数 | 200 | 「直近だけ遡れればいい」の具体化 |
| 保持するセッション数 | 20 | 最終書き込みが古い順に丸ごと捨てる |
| 1 イベントのテキスト | 8 KB で切る | 1 行が肥大しないための上限。プラットフォーム側の行サイズ上限は測っていないが、この上限はそれよりはるかに小さい |

トリムは書き込みのたびに行う。

## 通知履歴との合成

同じ内容が 2 経路で届く。`completed` push の `bodyFull` と `assistant` イベントは同じ文章である。

**片方で置き換えてはいけない**。性質が違う：

| | 通知履歴 | イベントバッファ |
|---|---|---|
| 保存 | 恒久（端末に残る） | 直近 N 件だけ |
| 届く条件 | アプリが閉じていても | 前面のときだけ |
| 答えられるか | `asking` は Allow/Deny/選択肢に答えられる | 答える経路なし |

だから合成する。重複は `eventId` で潰す — 同じ id を持つ通知アイテムは描画しない。

**`asking` には手を触れない**。答えられる唯一の経路であり、イベント列に代替がない。

**採らない案**：「watcher が繋がっている間は push を止める」。電話はいつバックグラウンドに落ちるか分からないので、配信を競合状態に賭けることになる。

---

## 壊れ方と、それぞれの答え

| 壊れ方 | 答え |
|---|---|
| バッファが際限なく伸びる | 書き込みのたびに上限へトリム（上表） |
| 壊れたイベント | 既存のスナップショット検査と同じ形で**保存前に**弾く。壊れた値を保存すると電話に配り返すことになり、過去に watch ソケットを恒久的に殺した形と同じ |
| 電話の再接続 | `seq > n` で再開 |
| 要求された seq がバッファの先頭より古い | 応答に**保持している最古の seq を必ず載せる**。電話はそれが要求値より大きければ穴だと判定できる。黙って部分列を返すと電話が連続だと誤って繋ぐ |
| watcher が誰もいない | それでも保存する。DO 側にバッファを置いた前提そのもの |
| publisher ソケット切断中のイベント | 落とす（上述の受け入れた欠点） |
| 巨大な 1 通 | 8 KB で切る |

## テスト

**worker**：seq の単調増加／トリムが新しい方を残す／古すぎる seq に穴を報告する／壊れたイベントを保存しない／セッション上限の追い出し／長文の切り詰め。

**Swift probe**：どのフレームがどのイベントになるか。**特に `user` フレームから tool_result を除外する判定**を固定する。一行要約に何が入り何が入らないか。

**電話**：`eventId` による重複排除、`seq` 順の並び、穴の扱い。

いずれも、テスト数の floor（`EXPECTED_TESTS` / `EXPECTED_SWIFT_TESTS`）を実測値に上げる。

## Mac の外に出るデータ

**この設計は「何が Mac の外に出るか」を実質的に変える。**今日 relay に渡っているのは完了時の 1 通と許可要求だけ。この設計では**アシスタントの発言すべてとユーザーの発言すべて**が Cloudflare を経由し、DO の SQLite に最大 200 件保存される。

ツールについては、上の表に列挙したぶんだけが通る — **`Bash` のコマンド行と、読み書きしたファイルの「ファイル名」が外に出る**。これは「ツールの詳細は要らない」という当初の言葉より広く、選択された解像度（`Bash: npm test` / `Edit: SessionStore.swift`）に合わせた結果である。狭めたいなら表の行を削るだけでよく、既定が「名前だけ」なので削る方向は安全である。

どのツールでも通らないもの：ディレクトリを含む絶対パス、ファイル内容、差分、ツールの実行結果、列挙にないツールの引数。

## 実測（2026-09-06）

**デプロイ済み relay に対する実配線テストは通った。** 使い捨ての machine id で publisher と watcher の実ソケットを開き、次を確認した（`scratchpad/relay-event-probe.mjs`、worker version `5e7c9705`）。

- publisher が送ったイベントが watcher に届き、relay が `seq` を振っている
- テキストと `at`（Swift の 2001 年起点の秒、小数込み）が往復で変わらない
- `events_since 0` がイベントと `oldestSeq` を返す
- 最新 seq より後を要求すると空が返る
- **形が壊れたイベントは保存されない** — その後の backfill にも現れない

そのスクリプトには `check(..., true)` と書いた行が 1 つ混ざっており、**あれは何も測っていない**。PASS と表示されるが証拠ではない。

**実機の目視 4 項目は未確認。** Canopy の Debug ビルドと iPhone の新ビルドは動いているが、セッションで 1 turn 走らせる操作が要る。次の 4 つを人が確かめる必要がある。

1. アシスタントの発言が完成時点で電話に現れること
2. ツール行にコマンドとパスが出ていないこと（`Bash: npm test` は出てよく、`/Users/...` は出てはいけない）
3. 完了 push と同じ文章が 2 つ並ばないこと
4. **Mac で打ったプロンプト自身が `user` イベントとして出ること** — これは推論であって実測ではない。出なければ `SessionEvent` の `user` ケースは死にコードであり、拡張が何を送っているかを `[stdout→webview] type=` のログで数えて直す

## 見つけもの（本体には入れない）

**タイムラインの穴**。1 時間アプリを閉じた後に開くと、1 時間前の疎な `completed` と直近の密なイベントが 1 本に並ぶ。「ここに穴がある」の印は後から足せる。

**`apns-expiration: "0"`**。relay は「今すぐ配信できなければ捨てる」を送っている。端末が本当にオフラインだと通知が保存されず消える。この設計とは別経路の取りこぼしで、別途判断する。

**APNs の throttle 窓**。429 のリトライ待ち時間が 1 秒では不足すると実測済み。実データを見てから決める。
