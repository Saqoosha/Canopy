# Canopy のセッションを Slack スレッドに紐付け、スレッドの参加者が直接質問できるようにする

例：委託契約のスレッド（`C089F5P7R9P`）で話している内容を、outsourcing-contract セッションに直接聞けるようにする。Saqoosha がスレッドの内容をコピーしたり「スレッド見て」と頼んだりしなくて済む。

質問するのは Saqoosha 本人とは限らない。セッションは Saqoosha の Mac の上で、Saqoosha の権限のまま動いている。だから設計の中心は、他人の質問にセッションが何をしてよいかを決めること。

## 実測したこと（2026-10-22）

- **Saqoolaude の権限**: `channels:history` / `groups:history` と、`message.channels` / `message.groups` のイベントを持っている。だからスレッドを読めるし、メンションも受け取れる。`app_mention` は購読していないので、本文に bot の user id があるかどうかで判定する。
- **ツールの拒否**: `tool.call` に `{ deny }` を返すと、`acceptEdits` でも Edit と Bash が止まった。拒否の理由はモデルに届き、モデルはそれを読んで答え方を変えた。
- **分類**: `prompt.submit` の中で `$.model.complete({ model: 'haiku' })` が動いた。所要時間は約 0.9 秒。結果を `context` に足すと、モデルはそれを読んで答えに反映した。
- **Grep と Glob が無い**: Canopy が使う同梱の CLI（2.1.307）にも、PATH 上の 2.1.287 にも、Grep / Glob のツールが無い。検索は Bash 経由になる。だから Slack の質問に答えるセッションは、名前が分かっているファイルを Read することしかできない。

## 構成

```
Slack thread ──event──▶ Saqoolaude Worker ──WebSocket──▶ canopyd ──▶ ShimProcess ──▶ CLI
     ▲                    (CanopyBridge DO)   (canopyd から外向きに張る)  (電話の返信と同じキュー)
     └──── 承認済みの返信 ◀── Saqoolaude ◀── 下書きの DM ◀───────── ターンの最後の発言
```

- **紐付け**: ペインメニューの「Connect to Slack Thread…」で permalink を貼る。紐付けは Worker の DO が `channel:threadTs` ごとに持つ。中身は session key と、質問できる人。Canopy の側からしか作れない（control の動詞はローカルのクライアント限定）。
- **受け付けないセッション**: SSH remote のセッション、門番の `ready` がまだ届いていないセッション、bypass モードのセッション。この 3 つは、紐付けるときも、質問が来たときも拒否する（本人の質問は門番を通らないので、この確認もしない）。
- **転送**: `canopy.slackBridgeEnabled` が有効な Mac の daemon が、Worker へ WebSocket を張る。認証には Saqoolaude MCP の固定キーを使い、MCP と同じ helper で読む。daemon はホスト名を `?mac=` に付けて接続し、Worker は Mac の名前ごとに 1 本の接続を持つ。紐付けは作った Mac を覚えていて、質問はその Mac に届く。同じ名前の daemon が二重につないだときだけ、前の接続が閉じられる（閉じられた側は再接続しない）。
- **受信**: 紐付けたスレッドで bot をメンションしたメッセージだけを受け取る。同じイベントが重なって届いたら 1 回として扱う。
- **注入**: Worker は、前回の質問以降のスレッドの発言を集める。daemon はそれに印と質問者の名前を付けて、`send_message` と同じ経路でセッションに注入する（本人の質問だけは印を付けない。下の「Saqoosha 本人の質問」）。同じセッションへの質問は、1 つずつ順番に処理する。
- **返信**: ターンの最後の発言を下書きにして、Saqoosha に DM で送る（本人の質問はスレッドに直接出す）。✅ ならスレッドに投稿し、❌ なら破棄する。全員への通知の記法（`<!channel>` など）は、文字に置き換える。35 分たっても答えが無い質問は、Worker の側で打ち切る。

## ガードレール

### 層 1：受信した質問の分類（canopy-bridge mod、`prompt.submit`）

- 印の付いたプロンプトを、Haiku で 4 種類に分類する。質問、変更依頼、情報の持ち出し、指示の注入。
- 結果は `[filter]` の注記として、モデルだけに渡す。下書きの DM にも載せる。
- 分類に失敗したら `unknown` とする。ターンは止めない。止めるのは層 2 の役目。

### 層 2：ツールの門番（canopy-bridge mod、`tool.call`）

印の付いたプロンプトが来てから、Saqoosha が待機中のセッションに印の無いプロンプトを送るまで、次の規則が効く。実行中のターンに合流したプロンプト、隠れたプロンプト、スラッシュコマンドでは解除されない。規則はすべて決定的で、LLM の判定はどこにも使わない。

- **通す**: cwd の中のファイルの Read だけ。パスは `~` を展開し、symlink を解決してから判定する。
- **拒否**:
  - 認証情報らしい名前を含むパス。判定は cwd から下の部分だけで行う（`~/repos/token-service` のような置き場所の名前では止めない）。名前と解決後の実体の両方を見る。
  - cwd の外を対象にするもの。
  - cwd がホームフォルダか、それより上にあるセッション。
  - Read 以外すべて。Bash、Grep、Glob も含む。Grep / Glob は今の CLI に無く、glob の解釈を ripgrep と完全に揃える手間に見合わない。
- **印の位置**: 印が本文のどこにあっても門番を張る。キューに溜まったプロンプトは、連結されて届くことがあるため。
- **門番の中で例外が起きたら**: 拒否として扱う。
- **理由を返す**: 拒否するときは理由を `deny` に書く。モデルはそれを読んで答え方を変える。承認は一切しない。
- **印は Canopy が付ける**: Slack の本文から印を外すことはできない。Saqoosha が手で `[canopy:slack]` と書いても、制限が増えるだけ。

### 層 3：下書きの承認

本人以外の質問は、Saqoosha が ✅ を付けるまで、スレッドには何も出ない。

### 質問できる人

紐付けた直後は Saqoosha だけ。ほかの人は、最初の質問のときに Saqoosha に DM で許可を聞く。✅ ならその人を許可リストに足して、保留していた質問を流す。許可はスレッドごとに持つ。紐付けのときに人を選ばせないのは、Canopy からは Slack の人の一覧が見えないため。

### Saqoosha 本人の質問

Mac で打つのと同じに扱う。Worker が Slack の user ID で本人と確かめた質問は、印を付けずに普通のプロンプトとして渡るので、門番は掛からず、全ツールで動く。答えは下書きを挟まずにスレッドへ直接出る。他人の文がそのターンを動かせないように、スレッドの差分には本人の発言だけを入れる。危険は、Slack のアカウントを乗っ取られると、その Mac で何でも動かせること（2026-10-22 に Saqoosha が了承）。

### 質問者に見えるもの

- 受け取った質問に 👀 を付ける。投稿されたら ✅、見送り・オフライン・拒否なら ❌ に替える（`reactions:write`）。
- セッションに渡す質問者の名前は `users.info` で引く（`users:read`）。どちらのスコープも 2026-10-22 に足した。

## 範囲外（findings）

- 読み取り専用の Bash（`rg`、`ls` など）を、決まった形だけ許すこと。今の CLI では、検索の手段がこれしかない。
- 紐付けごとの自動投稿モード。
- DM の中での下書きの編集。
- チャンネル単位の紐付け。
