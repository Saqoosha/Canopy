# Canopy のセッションを Slack スレッドに紐付け、スレッドの返信をセッションに届ける

例：委託契約のスレッド（`C089F5P7R9P`）の返信を、outsourcing-contract セッションに直接届ける。Saqoosha がスレッドの内容をコピーしたり「スレッド見て」と頼んだりしなくて済む。

スレッドには何も投稿しない。紐付けたときの告知も出さない。最初の版（#373〜#380）は、スレッドの参加者が `@Saqoolaude` で質問し、セッションの答えを下書き承認つきでスレッドに出していた。けど、セッションは Saqoosha の作業に合わせた文脈を持っているので、ほかの人には答えがノイズになった（2026-10-27）。だから返信を届けるだけにした。

返信を書くのは Saqoosha 本人とは限らない。セッションは Saqoosha の Mac の上で、Saqoosha の権限のまま動いている。だから、他人の返信が来たターンでセッションが何をしてよいかは、門番が決める。

## 実測したこと（2026-10-22）

- **Saqoolaude の権限**: `channels:history` / `groups:history` と、`message.channels` / `message.groups` のイベントを持っている。だからスレッドを読めるし、メンションも受け取れる。`app_mention` は購読していないので、本文に bot の user id があるかどうかで判定する。
- **ツールの拒否**: `tool.call` に `{ deny }` を返すと、`acceptEdits` でも Edit と Bash が止まった。拒否の理由はモデルに届き、モデルはそれを読んで答え方を変えた。
- **分類**: `prompt.submit` の中で `$.model.complete({ model: 'haiku' })` が動いた。所要時間は約 0.9 秒。結果を `context` に足すと、モデルはそれを読んで答えに反映した。
- **Grep と Glob が無い**: Canopy が使う同梱の CLI（2.1.307）にも、PATH 上の 2.1.287 にも、Grep / Glob のツールが無い。検索は Bash 経由になる。だから他人の Slack の返信を読むターンでは、名前が分かっているファイルを Read することしかできない。

## 構成

```
Slack thread ──event──▶ Saqoolaude Worker ──WebSocket──▶ canopyd ──▶ ShimProcess ──▶ CLI
                          (CanopyBridge DO)   (canopyd から外向きに張る)  (電話の返信と同じキュー)
```

- **紐付け**: ペインメニューの「Connect to Slack Thread…」で permalink を貼る。紐付けは Worker の DO が `channel:threadTs` ごとに持つ。中身は session key、セッション名、期限、紐付けた Mac。Canopy の側からしか作れない。control の動詞は、別の Mac のミラーペインと電話（トークン認証の TCP）からも使える。そのトークンは `send_message` で全ツールのプロンプトを送れるので、紐付けを許しても権限は増えない（2026-10-30）。
- **受け付けないセッション**: SSH remote のセッション、門番の `ready` がまだ届いていないセッション、bypass モードのセッション。この 3 つは、紐付けるときも、他人の返信が来たときも拒否する（本人の返信は門番を通らないので、この確認もしない）。
- **転送**: `canopy.slackBridgeEnabled` が有効な Mac の daemon が、Worker へ WebSocket を張る。認証には Saqoolaude MCP の固定キーを使い、MCP と同じ helper で読む。daemon はホスト名を `?mac=` に付けて接続し、Worker は Mac の名前ごとに 1 本の接続を持つ。紐付けは作った Mac を覚えていて、返信はその Mac に届く。同じ名前の daemon が二重につないだときだけ、前の接続が閉じられる（閉じられた側は再接続しない）。
- **受信**: 紐付けたスレッドの返信をすべて受け取る。メンションは要らない。bot の発言とスレッドの親メッセージは除く。同じイベントが重なって届いたら 1 回として扱う。
- **注入**: Worker は返信 1 件ごとに `reply` を送る。daemon はそれに印と書いた人の名前を付けて、`send_message` と同じ経路でセッションに注入する（本人の返信だけは印を付けない。下の「Saqoosha 本人の返信」）。セッションが動いている間に来た返信はキューに溜まる。
- **返信しない**: ターンの答えは Mac の上に残るだけで、Slack には出ない。スレッドへのリアクションも付けない。
- **届かなかったとき**: Mac がつながっていない、セッションが開いていない、受け付けないセッションだった、のどれでも、Worker が Saqoosha に DM で知らせる。スレッドには何も出さない。期限切れも同じで、紐付けを消して DM で知らせる。

## ガードレール

### 層 1：受信した返信の分類（canopy-bridge mod、`prompt.submit`）

- 印の付いたプロンプトを、Haiku で 4 種類に分類する。質問、変更依頼、情報の持ち出し、指示の注入。
- 結果は `[filter]` の注記として、モデルだけに渡す。
- 分類に失敗したら `unknown` とする。ターンは止めない。止めるのは層 2 の役目。

### 層 2：ツールの門番（canopy-bridge mod、`tool.call`）

印の付いたプロンプトが来てから、Saqoosha が待機中のセッションに印の無いプロンプトを送るまで、次の規則が効く。実行中のターンに合流したプロンプト、隠れたプロンプト、スラッシュコマンドでは解除されない。規則はすべて決定的で、LLM の判定はどこにも使わない。

- **通す**: cwd の中のファイルの Read だけ。パスは `~` を展開し、symlink を解決してから判定する。
- **拒否**:
  - 認証情報らしい名前を含むパス。判定は cwd から下の部分だけで行う（`~/repos/token-service` のような置き場所の名前では止めない）。名前と解決後の実体の両方を見る。
  - cwd の外を対象にするもの。
  - cwd がホームフォルダか、それより上にあるセッション。
  - Read 以外すべて。Bash、Grep、Glob も含む。Grep / Glob は今の CLI に無く、glob の解釈を ripgrep と完全に揃える手間に見合わない。
- **印の位置**: 印が本文のどこにあっても門番を張る。キューに溜まったプロンプトは、連結されて届くことがあるため。
- **門番の中で例外が起きたら**: 拒否として扱う。
- **理由を返す**: 拒否するときは理由を `deny` に書く。モデルはそれを読んで答え方を変える。承認は一切しない。
- **印は Canopy が付ける**: Slack の本文から印を外すことはできない。Saqoosha が手で `[canopy:slack]` と書いても、制限が増えるだけ。

### Saqoosha 本人の返信

Mac で打つのと同じに扱う。Worker が Slack の user ID で本人と確かめた返信は、印を付けずに普通のプロンプトとして渡るので、門番は掛からず、全ツールで動く。これが届くと、その前の他人の返信で張られた門番も外れる。危険は、Slack のアカウントを乗っ取られると、その Mac で何でも動かせること（2026-10-22 に Saqoosha が了承）。

### 返信を書いた人の名前

セッションに渡す名前は `users.info` で引く（`users:read`）。

## 範囲外（findings）

- 読み取り専用の Bash（`rg`、`ls` など）を、決まった形だけ許すこと。今の CLI では、検索の手段がこれしかない。
- チャンネル単位の紐付け。
