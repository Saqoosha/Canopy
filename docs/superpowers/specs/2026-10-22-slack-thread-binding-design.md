# Canopy のセッションを Slack スレッドに紐付け、スレッドの返信をセッションに届ける

例：委託契約のスレッド（`C089F5P7R9P`）の返信を、outsourcing-contract セッションに直接届ける。Saqoosha がスレッドの内容をコピーしたり「スレッド見て」と頼んだりしなくて済む。

スレッドには何も投稿しない（Saqoosha が許可した人の依頼に答えるときを除く。下の「Saqoosha が許可した人の返信」）。紐付けたときの告知も出さない。最初の版（#373〜#380）は、スレッドの参加者が `@Saqoolaude` で質問し、セッションの答えを下書き承認つきでスレッドに出していた。けど、セッションは Saqoosha の作業に合わせた文脈を持っているので、ほかの人には答えがノイズになった（2026-10-27）。だから返信を届けるだけにした。

返信を書くのは Saqoosha 本人とは限らない。セッションは Saqoosha の Mac の上で、Saqoosha の権限のまま動いている。だから、他人の返信が来たターンでセッションが何をしてよいかは、門番が決める。

## 実測したこと（2026-10-22）

- **Saqoolaude の権限**: `channels:history` / `groups:history` と、`message.channels` / `message.groups` のイベントを持っている。だからスレッドを読めるし、メンションも受け取れる。`app_mention` は購読していないので、本文に bot の user id があるかどうかで判定する。
- **ツールの拒否**: `tool.call` に `{ deny }` を返すと、`acceptEdits` でも Edit と Bash が止まった。拒否の理由はモデルに届き、モデルはそれを読んで答え方を変えた。
- **分類**: `prompt.submit` の中で `$.model.complete({ model: 'haiku' })` が動いた。所要時間は約 0.9 秒。結果を `context` に足すと、モデルはそれを読んで答えに反映した。
- **Grep と Glob が無い**: Canopy が使う同梱の CLI（2.1.307）にも、PATH 上の 2.1.287 にも、Grep / Glob のツールが無い。検索は Bash 経由になる。だから他人の Slack の返信を読むターンでは、名前が分かっているファイルを Read することしかできない。

## 構成

```
Slack thread ──event──▶ Saqoolaude Worker ──WebSocket──▶ canopyd ──▶ ShimProcess ──▶ CLI
                          (CanopyBridge DO)   (canopyd から外向きに張る)  (電話の返信と同じキュー)
```

- **紐付け**: ペインメニューの「Connect to Slack Thread…」で permalink を貼る。紐付けは Worker の DO が `channel:threadTs` ごとに持つ。中身は session key、セッション名、期限、紐付けた Mac。Canopy の側からしか作れない。control の動詞は、別の Mac のミラーペインと電話（トークン認証の TCP）からも使える。そのトークンは `send_message` で全ツールのプロンプトをもう送れる。ただし紐付けは、パスワードをリセットしても期限まで残る（2026-10-30）。
- **受け付けないセッション**: SSH remote のセッション、門番の `ready` がまだ届いていないセッション、bypass モードのセッション。この 3 つは、紐付けるときも、他人の返信が来たときも拒否する（本人の返信は門番を通らないので、この確認もしない）。
- **転送**: `canopy.slackBridgeEnabled` が有効な Mac の daemon が、Worker へ WebSocket を張る。認証には Saqoolaude MCP の固定キーを使い、MCP と同じ helper で読む。daemon はホスト名を `?mac=` に付けて接続し、Worker は Mac の名前ごとに 1 本の接続を持つ。紐付けは作った Mac を覚えていて、返信はその Mac に届く。同じ名前の daemon が二重につないだときだけ、前の接続が閉じられる（閉じられた側は再接続しない）。
- **受信**: 紐付けたスレッドの返信をすべて受け取る。メンションは要らない。bot の発言とスレッドの親メッセージは除く。同じイベントが重なって届いたら 1 回として扱う。
- **注入**: Worker は返信 1 件ごとに `reply` を送る。daemon はそれに印と書いた人の名前（と、形が合えば Slack の ID とスレッド）を付けて、`send_message` と同じ経路でセッションに注入する（本人の返信だけは印を付けない。下の「Saqoosha 本人の返信」）。セッションが動いている間に来た返信はキューに溜まる。
- **返信しない**: ターンの答えは Mac の上に残るだけで、Slack には出ない（許可した人の依頼では、モデルが同じスレッドに `slack_post` で返信できる）。スレッドへのリアクションも付けない。
- **届かなかったとき**: Mac がつながっていない、セッションが開いていない、受け付けないセッションだった、のどれでも、Worker が Saqoosha に DM で知らせる。スレッドには何も出さない。期限切れも同じで、紐付けを消して DM で知らせる。

## ガードレール

### 層 1：受信した返信の分類（canopy-bridge mod、`prompt.submit`）

- 印の付いたプロンプトを、Haiku で 4 種類に分類する。質問、変更依頼、情報の持ち出し、指示の注入。
- 結果は `[filter]` の注記として、モデルだけに渡す。
- 分類に失敗したら `unknown` とする。ターンは止めない。止めるのは層 2 の役目。
- 許可した人の返信では、関連があるかも一緒に聞く（下の「Saqoosha が許可した人の返信」）。

### 層 2：ツールの門番（canopy-bridge mod、`tool.call`）

印の付いたプロンプトが来てから、Saqoosha が待機中のセッションに印の無いプロンプトを送るまで、次の規則が効く。スキルのようにターンを始めるスラッシュコマンドでも解除する。実行中に打ったコマンドはターンの終了後に届くので、そこで解除する。実行中のターンに合流したプロンプト、隠れたプロンプト、予約実行のプロンプト、Canopy の keep-alive では解除されない。`/compact`、`/context`、fork で動くスキルは `prompt.submit` を通らないので、解除しない。何かを通す判定に LLM は使わない。LLM を使うのは、許可した人の返信から許可を外すときだけ（下の「Saqoosha が許可した人の返信」）。以下は許可が無いときの規則。

- **通す**: cwd の中のファイルの Read だけ。パスは `~` を展開し、symlink を解決してから判定する。
- **拒否**:
  - 認証情報らしい名前を含むパス。判定は cwd から下の部分だけで行う（`~/repos/token-service` のような置き場所の名前では止めない）。名前と解決後の実体の両方を見る。
  - cwd の外を対象にするもの。
  - cwd がホームフォルダか、それより上にあるセッション。
  - Read 以外すべて。Bash、Grep、Glob も含む。Grep / Glob は今の CLI に無く、glob の解釈を ripgrep と完全に揃える手間に見合わない。
- **印の位置**: 印と、それに続く定型文（`ControlProtocol.slackPrefix`）が本文のどこにあっても門番を張る。キューに溜まったプロンプトは、連結されて届くことがあるため。印だけの引用（この機能について話す peer セッションのメッセージなど）では張らない（2026-10-30）。サブエージェントの報告（`task-notification`）、予約実行、CLI の peer メッセージが定型文を行の途中で引用しているときも張らない。行頭にあれば、連結された返信として張る（2026-11-05）。
- **門番の中で例外が起きたら**: 拒否として扱う。
- **CLI の再起動**: 門番の状態はセッション ID ごとに `$.store` へ書き、`--resume` で起動した CLI が読み戻す。読めなければ門番を張る。書けなければ動作中の門番は残るが、再起動で消える（Canopy のログに残る）。fork は別のセッション ID になるので引き継がない。
- **理由を返す**: 拒否するときは理由を `deny` に書く。モデルはそれを読んで答え方を変える。承認は一切しない。
- **印は Canopy が付ける**: Slack の本文から印を外すことはできない。Saqoosha が手で定型文ごと書いても、制限が増えるだけ。

### Saqoosha 本人の返信

Mac で打つのと同じに扱う。Worker が Slack の user ID で本人と確かめた返信は、印を付けずに普通のプロンプトとして渡るので、門番は掛からず、全ツールで動く。これが届くと、その前の他人の返信で張られた門番も外れる。危険は、Slack のアカウントを乗っ取られると、その Mac で何でも動かせること（2026-10-22 に Saqoosha が了承）。

### Saqoosha が許可した人の返信（2026-11-19）

Kenja では、保坂さんの修正依頼が来るたびに Saqoosha が「go」と打っていた。デプロイまで通らないと、保坂さんは結果を見られない。だから Saqoosha が許可した人の依頼は、Saqoosha を待たずに編集・確認・デプロイ・スレッドへの返信まで進める。

- **許可**: セッションで `/slack-allow <名前か Slack ID> [deploy]` と打つ。名前は、このセッションに返信を書いた人から引く。空白を含む名前もそのまま書ける（末尾の `deploy` だけが指定）。完全一致を優先し、部分一致が 2 人以上なら何もしない。数字を含まない語（`UMEDA`）は ID ではなく名前として扱う。`/slack-allow` だけで一覧、`off <名前>` で取り消し、`off` で全部取り消す。セッション ID ごとに `$.store`（`slack-grants:<id>`）に置く。書けるのは人の送ったプロンプト（`PERSON_ORIGINS`: `composer` / `bridge` / `sdk`）だけで、モデルの `Skill` 呼び出しはいつでも拒否する。`sdk` には `send_message` も入るので、control の口を持つクライアント（ミラー、電話）からも書ける。そのクライアントは門番の無いプロンプトをもともと送れる
- **誰か**: daemon は Worker が送る `user` / `channel` / `threadTs` を、形を確かめてからプロンプトの 1 行目に入れる（`ControlProtocol.SlackSource`）。ID は名前より前に置くので、表示名に何を書いても ID の位置は動かない。ID の無い行（古い daemon、ミラーの `send_message`）は誰でもない扱いで、名前が同じでも許可しない。形が合わずに捨てたときは daemon のログに残る。表示名は本人が変えられるので、許可の返事に出る ID で本人か確かめる
- **本人扱いにしない**: 印と名前は残る。モデルは誰の依頼かを知ったまま動き、報告にも書き手が残る
- **効く範囲**: 許可はその返信のターンだけ。次の印の付いたプロンプトで判定し直し、通知・peer・予約実行など印の無いプロンプトが来たら外す。ツールを呼ぶたびに `slack-grants` を読み直すので、`/slack-allow off` や `deploy` を外す操作は、動いているターンにもすぐ効く
- **関連チェック**: 許可された人の返信だけ、Haiku に分類と一緒に「このセッションの作業についての依頼か」を聞く（直近 12 件の会話を渡す）。答えがちょうど `QUESTION RELATED` か `CHANGE_REQUEST RELATED` のときだけ許可が効く。ほかの答え、答えが無いとき、6000 文字（Haiku に渡す長さ）を超えるプロンプト、読めないフォルダのセッションでは許可しない。判定は許可を取り消すほうにしか使わない。言いくるめられても、Saqoosha が許した範囲より広くはならない
- **混ざったとき**: 1 つのプロンプトに許可の無い人の返信が混ざっていれば、全体を読み取りだけにする。読み取りだけになった返信のあとに来た返信も、Saqoosha が門番を外すまで読み取りだけ（前の本文が文脈に残っているため）。この「読み取りだけの返信が残っている」は専用の印で持つ（gate のキーの値 `'held'`）。keep-alive や通知で許可が外れただけなら、次の許可した人の返信はまた許可を得られる
- **許可で通るもの**: cwd の中の Read / Edit / Write / MultiEdit / NotebookEdit（認証情報らしい名前の規則は Read と同じ。書き込みは、まだ無いファイルなら、存在する一番近い祖先のフォルダの symlink を解決してから判定する）、Bash、`TodoWrite`、`ToolSearch`、同じスレッドへの `mcp__saqoolaude__slack_post`（permalink で、`channel` も `broadcast` も `notify_channel` も `reply_in_thread: false` も無し）。パスやコマンドの無い呼び出しは拒否する
- **書き込みで拒否するもの**: あとのターンやセッションを動かすファイル（`.claude/` `.git/` `.husky/` `.github/` `.vscode/` `CLAUDE.md` `AGENTS.md` `.mcp.json` `.envrc` `lefthook.yml`）と、覚えたデプロイの中身を決めるファイル（`package.json` `Makefile` `justfile` `wrangler.*` `cloudflare.config.*` `*.sh`）。Bash からの書き込みは、下の「覚えたコマンドだけ」で止まる
- **Bash は覚えたコマンドだけ**: 禁止リストでは Bash を閉じ込められなかった（`bash -c "curl …"`、`/usr/bin/env`、`curl localhost evil.example`、`sed -i … package.json` が、2 回のレビューで次々にすり抜けた）。だから許可した人のターンの Bash は、このセッションで Saqoosha が始めたターンにすでに成功したコマンドだけ通す。Saqoosha は各プロジェクトのビルドやデプロイのコマンドを覚えていないので、セッションが覚える。代わりに、書き方が少し違うコマンドは拒否され、Saqoosha に回る
  - **覚えるもの**: 人の送ったプロンプトで始まり門番の無いターンで、フォアグラウンドで成功した Bash の単純コマンド全部（`slack-commands:<id>`、新しい 300 件）。`/slack-allow <名前>` で許可を出すときだけ、会話の履歴からも拾い、何件拾ったかを返事に出す（新しい mod より前に流したもの。履歴は誰のターンかを持たない）。一覧では拾わない
  - **比べ方**: 単純コマンドごとに、同じ行の `cd` で動いたフォルダ（セッションのフォルダからの相対。`( … )` と `$( … )` の中の `cd` はその中だけ。外への絶対パス、`cd ~`、`cd -`、`||` の直前の `cd` のあとは「わからない」で、何とも一致しない。`|` や `&` の前後の `cd` はサブシェルで終わるのでフォルダを変えない）と、語の並びを比べる。行き先だけの `cd` 自体は比べない（リダイレクトなどが付いた `cd` は比べる）。区切りは `&&` `;` `|` `$(…)` などで、引用符・エスケープ・コメントの中では切らない。引用符は語に残すので、`echo 'x > package.json'` と `echo x > package.json` は別のコマンド。`do` `then` `time` などの前置きと、ファイルに書かないリダイレクト（`2>&1`、`>/dev/null`）は外す。ほかのリダイレクト、先頭の `VAR=`、引数は残すので、`echo x > package.json`、`X=prod cf deploy`、`cf deploy --env production` は、覚えたものとは別のコマンド。置換は `$SUB` という語になり、中のコマンドも 1 つずつ比べる
  - **デプロイ**: デプロイらしい語（`deploy` `publish` `release` `apply` `push` `upload`）を含むコマンドは、覚えていても `deploy` の許可が要る
  - **Saqoosha のもの**: `git` / `jj` の commit・push・worktree など、`op` `security` `ssh` `gh` `canopyctl` `sudo` `printenv` など、`/dev/tcp`、`rm -r`、`$HOME`、認証情報らしい名前を含むコマンドは、Saqoosha のターンで流れていても拒否する
  - **限界**: Bash の結果は行全体の成否しか持たないので、実行されなかった枝（`false && cf deploy; true`、`|| true` で隠れた失敗）のコマンドも覚える。覚えるのは Saqoosha のターンで Claude が書いたコマンドだけ。Bash の作業フォルダは呼び出しをまたいで残るので、`cd cms` と `cf deploy` を別の呼び出しで流すと、`cf deploy` はセッションのフォルダで流したものとして覚える。許可した人のターンでも同じ前提で比べる。ビルドは編集したファイルの中身を実行するので、編集の許可はそのぶんの実行も許す。許可したあとの呼び出しも、セッション自身の権限モードを通る
- **CLI の再起動**: 許可の中身は門番（`slack-gate:<id>`、`true` か `'held'`）とは別のキー（`slack-gate-grant:<id>`）に置き、`--resume` で読み戻す。外すときは許可のキーを先に消すので、書き込みが途中で失敗しても、残るのは読み取りだけの門番。このモジュールが書く形でなければ許可として扱わない

### 返信を書いた人の名前

セッションに渡す名前は `users.info` で引く（`users:read`）。

## 範囲外（findings）

- 読み取り専用の Bash（`rg`、`ls` など）を、決まった形だけ許すこと。今の CLI では、検索の手段がこれしかない。
- チャンネル単位の紐付け。
